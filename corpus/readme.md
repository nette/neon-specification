# NEON Conformance Corpus

Every implementation of NEON runs this corpus in its tests. A case is a set of files
with a common name in one of the category directories:

| directory | input | expectation | what is verified |
|---|---|---|---|
| `decode/` | `<name>.neon` | `<name>.json` | the value of the document |
| `errors/` | `<name>.neon` | `<name>.error` | the input is rejected with this message at this position |
| `encode/` | `<name>.json` | `<name>.neon`, `<name>.block.neon`, or `<name>.error` | the output of `encode()` in inline and block mode |
| `cst/` | `<name>.neon` | `<name>.dump` | the shape of the tree |
| `roundtrip/` | `<name>.neon` | `<name>.dump` | `print(parse(s)) === s`, decoding does not fail, and the tree is as dumped |
| `mutations/` | `<name>.neon`, `<name>.ops.json` | `<name>.expected.neon`, optionally `<name>.expected.json`, `<name>.expected.<n>.neon` and `.json` | the text after editing operations, and the value (spec/mutations.md §6) |

Inputs are bytes exactly as stored; `.gitattributes` keeps git from converting line
endings (files with CRLF have `crlf` in their name).


## Typed values (`.json`)

A value is written in an explicitly typed form, so that nothing depends on the JSON
parser of the host or on the order of object properties:

```
{"type": "null"}
{"type": "bool", "value": true}
{"type": "int", "value": "12345678901234567890"}     digits as a string, any size
{"type": "float", "value": "1.0"}                    shortest round-trip form; INF, -INF, NAN
{"type": "string", "value": "..."}
{"type": "date", "value": "2016-06-03 19:00:00 +02:00"}   the text of the literal
{"type": "entity", "value": <value>, "attributes": <list or map>}
{"type": "chain", "entities": [<entity>, ...]}
{"type": "list", "items": [<value>, ...]}
{"type": "map", "entries": [["key", <value>], ...]}
```

A map key is the canonical string of the key (`0x10` is `16`, `5.3` is `5.3`). An array
whose keys are exactly 0..n-1 in order is always a `list`, never a `map`. An empty
array is a `map` when it was written with `{`, otherwise a `list`.

Values are compared by the equality of the specification: an integer is not equal
to a float (`1` is not `1.0`), the order of entries matters, and dates are equal
component by component, including the presence of an offset and the written fraction.


## Errors (`.error`)

The first line is the message without position, the second line is `line:column`,
both 1-based and counted in Unicode code points.


## Case metadata (`<name>.case.json`)

Metadata never go into the input, because they would change its lines and trivia:

```json
{
	"schema": 1,
	"hosts": ["js", "php"],
	"php3": "fixed",
	"reason": "why the case is limited or deviates",
	"indentation": "  ",
	"blockMode": 2
}
```

- `hosts` limits the case to the listed implementations (`js`, `php`, `py`, `go`, `rs`);
  it requires `reason`.
- `php3` classifies a deviation from nette/neon 3.x, the historical baseline:
  `fixed` (an accepted fix of 3.x), `host` (a projection of the host) or `open`
  (not decided yet; a runner reports it as a failure). It requires `reason`.
- `indentation` is the indentation passed to `encode()` (default tab).
- `blockMode` is the depth of blocks for the `<name>.block.neon` of an `encode/` case (default
  `true`, every level; encoding.md §2.1). nette/neon 3.x has no depth, so such an expectation is
  written by hand and the oracle checks only the inline one.

A runner is strict: an empty category, an expectation without its input, an unknown
`type`, `op` or `schema` are failures, not skipped cases.


## Where the expectations come from

The expectations of `decode/`, `errors/` and `encode/` are generated by
`tools/php-oracle.php` from nette/neon 3.4 in a pinned environment, recorded in
`oracle.json`. A case that deviates from 3.x carries a hand-written expectation and its
classification in the sidecar; the oracle verifies that 3.x still disagrees with it.
